Phase title: **Help page in plugin form**

## Technical Approach

The help page is produced by `renderHelp` in `src/help.js` from three parts: a hardcoded `INTRO`
(title and FROM ZERO), `routeLines()` (one row per leg, derived from `LEGS` and the bookings in
force), and a hardcoded `OUTRO` (WORDS, COMMANDS, the closing lines). The CLI verb `help` prints it,
and `/waybill:help` runs that verb through a `!` line, so there is one source and both callers see
the same bytes. That stays true.

This phase makes the page's text match `docs/ideation/help-plugin-form/help-target.txt`, which is
the page the operator approved, fitted to 80 columns. Three edits: FROM ZERO becomes four steps in
`/waybill:` form, COMMANDS becomes five `/waybill:` rows, and `routeLines()` gains a header row,
`#  LEG  CARRIER  STAMP`. WORDS, the closing lines, the section order and the leg rows are unchanged.

The header must take part in the column-width calculation. Widths are computed from the rows, and
when bookings cannot be read every carrier is `—`, which is narrower than the word `CARRIER`. A
header padded outside the calculation would then be misaligned. Work test-first: regenerate the
golden from the target and rewrite the literal assertions, see them fail, then edit `src/help.js`.

## Decisions Considered and Rejected

_Carried from the contract; consult before making gap decisions._

- **One slash-form help page for both the CLI verb and /waybill:help** — rejected: two renderings,
  with the terminal keeping the CLI forms. It needs flag plumbing on a verb that rejects all
  arguments, a changed bang line and a second golden for a form nobody reads.
- **Keep the page generated by src/help.js** — rejected: a static, hand-written page in
  commands/help.md. The copies would drift and ROUTE is derived from the bookings.
- **Change wording within the existing sections** — rejected: restructuring the page, for example
  merging FROM ZERO and COMMANDS. The problem is that the forms are wrong, not that the layout is.
- **FROM ZERO becomes four steps, with "move in" folded into the bay step** — rejected: keeping five
  steps with a reworded "move in" step. Once bay enters the bay (phase 2) there is no separate
  action for the operator to take.
- **Persist the approved help page as help-target.txt beside the contract, fitted to 80 columns** —
  rejected: leaving the strawman in the interview conversation and letting a later leg reword it.
  Fitting it shortened three FROM ZERO descriptions and kept `/waybill:next [<branch>]`; the wider
  `[<branch>[/<leg>]]` does not fit and is out of scope.
- **Archive add-help-card first, then write MODIFIED deltas against the living help-card spec** —
  rejected: editing the unarchived change in place. Phase 1 has done the archive.

### The ROUTE header row

**Pattern to follow**: the existing body of `routeLines()` in `src/help.js:85-103`.

**Overview**: Treat the header as one more row for width purposes, rendered by the same template.

```js
const HEADER = { index: '#', id: 'LEG', carrier: 'CARRIER', stamp: 'STAMP' };

function routeLines(bookings) {
  const legs = LEGS.map((leg, i) => { /* unchanged */ });
  const rows = [HEADER, ...legs];
  const width = (key) => Math.max(...rows.map((row) => [...row[key]].length));
  // pad, widths and the return template unchanged; they now run over `rows`
}
```

**Key decisions**:

- One template for header and legs, so alignment cannot drift.
- `#` in the index column: the leg-row tests match `^ +N +id ` on a digit, so a header that starts
  with a non-digit is not mistaken for a leg. `padStart` right-aligns it over the numbers.
- No separator line under the header: the page has seven spare lines, but the target has none and
  the request was for headers only.
- The `bookings could not be read:` note still follows the last leg row.

**Implementation steps**:

1. Add the header and alignment tests, including the unreadable-bookings case (the existing
   `survives a malformed overlay` test at 184-198 shows how to produce it). See them fail.
2. Add `HEADER` and run the width calculation over header plus legs.
3. Run the diff; it should be empty.

**Feedback loop**:

- **Playground**: `tests/help.test.js`.
- **Experiment**: bookings resolved (carrier column is 18 wide, header pads to it) and bookings
  unreadable (every carrier is `—`, so the column is 7 wide, set by `CARRIER`, and the rows pad to
  the header).
- **Check command**: `node --test tests/help.test.js`

## Failure Modes

| Component | Failure Mode | Trigger | Impact | Mitigation |
| --- | --- | --- | --- | --- |
| Header row | Misaligned header | Header padded outside the width calculation, bookings unreadable | Columns do not line up exactly when the operator is already lost | Header is a row in the same calculation; tested in both states. |
| Header row | Header counted as a leg | A test or consumer matching leg rows loosely | Wrong leg count | Header starts with `#`, not a digit; `lists every leg` runs unchanged. |
| Page text | A line over 80 columns | A machine's bookings overlay names a longer carrier than the stock ones | `fits one screen` is asserted only under the neutralised environment, so this is not a test failure; the page just wraps | Accepted, and unchanged by this phase: the carrier column was already data-driven. |
| Page text | `page.includes('waybill start')` passes vacuously | It always did; it guards a removed verb | None | Leave as is. |
| Golden | Golden and target drift | Editing one and not the other | The contract's target stops describing the page | The diff command in Validation Commands. |

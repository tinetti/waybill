Implementation Notes — Phase 5

Waybill Fleet · 2026-09-24 · live paint layer

Refresh loop — ps and tmux ride the fast lane, openspec alone is the slow one

Context
The spec leaves this open explicitly: “Decide whether the slow-lane cadence (~10s proposed) should differ for ps versus openspec. ps is cheap and could run on the fast lane; openspec is the expensive one.” The prose above it describes the slow lane as “openspec task counts and the ps process walk”.
Decision
Only the openspec lookup is on the slow lane. tmux and ps stay on the ~2s fast tick, because each is a single machine-wide call inside scanFleet (src/scan.js:285-288) whose cost does not grow with the fleet, whereas openspec is one subprocess per docket. Keeping them fast also makes the pane and activity columns track a pane you open while watching, which is what those columns are for. Splitting them out would have meant changing src/scan.js, and the spec's stronger instruction is that this phase “changes nothing below” the renderer.
Alternative
Add a signals: false option to scanFleet so the fast lane could skip both calls and a slow pass could fill them in. Rejected: it moves data logic into a phase that was scoped not to touch any, to save two calls that together measured 94 ms against a live tmux server with 1340 processes (Phase 3's own note).

Refresh loop — the deferred lane holds a finished docket one leg back

Context
Live mode scans with deferProgress, which makes the leg walk read the execute leg as unfinished until a count lands (src/inference.js:180-186). Phase 4 recorded the consequence at src/cli.js:362 and added that “a later frame can correct the first one”. Against this repository the difference is visible: fleet | cat reports feat/fleet-dashboard at 7/7 cleanup, live mode at 6/7 execute.
Decision
The slow lane corrects the bar and not the leg, which is exactly what this phase's spec asks of it — its own description of the lane is “the first frame goes up with whole-leg bars … the slow lane fills them in”, and its test list says “interpolated bars appear only after the slow lane lands”. A docket whose execute tasks are all ticked therefore sits at 6/7 execute in the live view with a full execute slice, until its bay is retired and it drops off. Flagged here rather than papered over: Phase 6's operator should judge whether that reads as wrong.
Alternative
Re-derive the leg in src/live.js once a count arrives complete, or run the slow lane as a full non-deferred scanFleet. The first duplicates the leg walk in the paint layer, which the spec forbids outright; the second is spawnSync per docket on the loop's own thread, freezing q for as long as it runs — the subprocess storm the two-lane split exists to prevent.

TTY fork — bin/waybill had to change, though the spec lists only src/cli.js

Context
The spec's Modified Files table names src/cli.js and tests/index.js and nothing else. But run now answers with a promise on the live path, and both entry points assign its result straight to process.exitCode, which rejects a non-integer.
Decision
Two entry points changed — bin/waybill and the self-exec block at the foot of src/cli.js — each wrapping the call in Promise.resolve(...).then(). Three lines apiece, no parser and no flag added, so the wrapper stays the thinnest file in the repository as its own comment insists.
Alternative
Keep run synchronous and have the live loop drive itself through process.exit. Rejected: it puts a hard exit inside library code, which is precisely what the wrapper's process.exitCode comment exists to avoid — a large frame on a pipe would be truncated.

TTY fork — the paint layer is imported statically, not on the live branch

Context
The spec says of the one-shot path: “The one-shot path does not import the paint layer at all.” Read literally that calls for a dynamic import() behind the io.isTTY check.
Decision
src/cli.js imports runLive statically, like every other module it dispatches to. The property that matters is behavioural — not one escape byte on a non-TTY stdout — and it is asserted directly, both in this phase's suite and in tests/fleet-dash-cmd.test.js. An unexecuted import emits nothing.
Alternative
await import('./live.js') inside the branch. Rejected: it makes the fleet handler asynchronous on both paths to buy a few hundred microseconds of module parse, and a lazily-loaded module is one the test suite can fail to notice is broken.

Validation — the diff-against-main check is measured against a moved target

Context
The spec's validation block asserts waybill status is untouched by diffing six paths against main — tests/cli.test.js, tests/waybill.test.js, tests/fleet.test.js and the three status goldens. That command now reports a large diff.
Decision
The diff is main moving, not this branch: main gained a stock review leg and an eight-leg route in 0c5c5fc after this branch was cut, so every golden on main reads of 8 where this branch reads of 7. Nothing in Phases 1-5 touched those files. Verified with the check the spec actually meant — the same six paths diffed against HEAD, which is clean — plus node --test tests/cli.test.js tests/waybill.test.js tests/fleet.test.js, which passes.
Alternative
Rebase the branch onto main so the spec's command runs as written. Out of scope for a phase, and it would fold an eight-leg route change into a dashboard branch; the rebase belongs to whoever opens the pull request.

Implementation Notes — Phase 1

Waybill Fleet · 2026-09-24 · Fleet model, multi-repo discovery, deferrable progress

Manual gate — ~/Projects is itself a git repository on this machine

Context
The spec's manual check asks for discoverRepos to be run against the real ~/Projects and the repository count confirmed. It returns exactly one entry: /Users/jtinetti/Projects. That directory has a .git of its own, so the "inside a repository, the answer is that repository" short circuit fires and the multi-repo walk never runs there. The same is true of every directory beneath it, including ~/Projects/tinetti.
Decision
Left as specified. The short circuit is the contract's stated rule, and overriding it here would be a behaviour change invented during implementation rather than agreed in the contract. Discovery itself is sound and fast — scanned against $HOME it found 3 repositories at depth 2 in 41 ms and 4 at depth 3 in 252 ms, with no duplicates.
Alternative
Have the fleet verb accept a flag that forces the multi-repo walk even inside a repository, or treat a repository whose own bays are empty as a scan root. Both are Phase 4 surface decisions, and Phase 6 is the gate where this has to be settled: on this operator's machine the dashboard will otherwise only ever show the ~/Projects repository's own dockets.

Deferred progress — the Open Item, answered

Context
The spec leaves open whether execute-leg done-ness can be decided without the task count in every case, or whether a docket can flip between frames.
Decision
It can flip, in both directions, so the Phase 4/5 renderer must tolerate a leg index changing between frames. Deferring makes the walk see total: 0, which legIsDone reads as unfinished, so a docket whose own change is fully ticked resolves to execute while deferred and to cleanup once the count lands. The reverse also exists: when only the openspec CLI knows about a change — no tasks.md on disk — the deferred walk sees changeId: null and reads the leg as done by stamp, where the synchronous path would have taken the CLI's counts. Both are accepted rather than designed around, as the spec's failure-mode table says.
Alternative
Resolve the counts from tasks.md during the walk and defer only the CLI refinement. That would make the two paths agree in the common case, but it puts two sources of truth in the same inference and leaves the disagreement visible in the rendered row instead of in the leg index.

The pending thunk resolves null when there is nothing to count

Context
The spec types the deferred value () => Promise<Progress|null> and requires that an absent or failing openspec binary "resolves to null rather than throwing". But executeProgress never returns null — with the CLI unavailable it falls back to counting tasks.md, and with nothing on disk it returns { done: 0, total: 0, changeId: null }.
Decision
The thunk maps "no change in flight" (changeId === null) and any thrown error onto null, and passes every real count through unchanged. That is the one signal the renderer needs — fall back to the whole-leg bar — and it makes the declared return type reachable.
Alternative
Return the 0 of 0 object verbatim and let the renderer special-case total === 0. Rejected: it pushes the same decision into every caller and leaves null in the type with nothing that ever produces it.

src/progress.js was not modified

Context
The spec's Modified Files table asks for executeProgress to be exported "in a form callable standalone against a repo root + change id, so the deferred lane can run it later".
Decision
No change was needed: executeProgress(repoRoot, changeId, changed) (src/progress.js:149) is already exactly that, and the deferred lane calls it as-is. Touching the file to satisfy the table would have been churn.
Alternative
Add a thin re-export or wrapper to match the table literally. Rejected as dead indirection.

RepoFleet carries a warnings array

Context
The spec's Data Model lists five fields on RepoFleet, while its Error Handling table requires that a repository with a malformed bookings overlay fall back to the built-ins "for that repo only, record a warning". There was nowhere to record it.
Decision
Added warnings: string[] as a sixth field. Per-repository rather than on FleetModel, because the fallback is a fact about one repository and the renderer attributes it to that group heading. The rest of the shape is untouched, so Phases 2 and 3 still treat it as append-only.
Alternative
Collect warnings on FleetModel. Rejected: it loses which repository is misconfigured, which is the only actionable part.

Dedup keys are resolved through symlinks, not only through git worktree list

Context
The spec's dedup rule covers bays — a .git file resolved to its main checkout. Its error table separately asks the walk to track visited real paths so a symlink cannot loop.
Decision
The discovered main checkout is also passed through realpathSync. A symlink such as ~/Projects/current -> ~/Projects/foo would otherwise be found as a second, differently named copy of a project that the loop guard does not catch — the guard only stops re-descending, not re-discovering. Covered by a fixture.
Alternative
Leave the discovered path as written. Rejected: a duplicated project is precisely the failure mode this phase exists to prevent, and the symlink route reaches it by a different door than the bay route.

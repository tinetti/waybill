Implementation Notes — Phase 2

Waybill Fleet · 2026-09-24 · Age and stacked-branch dependencies

Both modules — tryGit exported from src/repo.js

Context
The spec's Modified Files table names only src/scan.js, src/fleet.js and tests/index.js, and points at src/repo.js:71-89 as the pattern to follow. src/age.js and src/stack.js both need exactly the contract repo.js's private tryGit already has: run git, trim stdout, collapse every failure to null.
Decision
Export tryGit and import it in both new modules — a one-word change to a file the spec did not list. repo.js is already the read-only git-query module; a third and fourth private copy of the same four lines is the shape that eventually disagrees with itself about what a failed query is.
Alternative
Give each new module its own local helper, as bay.js:43 does. Rejected because bay.js has a documented reason for its copy — a mutation needs git's stderr, which tryGit throws away — and the new modules have no such reason.

openedAt — two git calls, because the single-call form needs a shell

Context
Implementation step 3 asks for git merge-base then git show -s --format=%ct, "or the single-call git log -1 --format=%ct $(git merge-base …) equivalent — measure and prefer the single call".
Decision
Two calls. The "single call" in the spec is a shell command substitution, which is two git processes plus a shell; every module here spawns git directly with an argv array and no shell, and git offers no log --merge-base that would collapse the two. Two direct spawns are strictly cheaper than the form the spec preferred, so there was nothing to measure.
Alternative
Spawn sh -c. Rejected: it adds a shell to a read-only query path for no gain, and every branch name would then need quoting.

trunkBase — retry the trunk as origin/<trunk>

Context
The spec passes the trunk as a branch name. defaultBranch answers with a name derived from origin/HEAD, which in a git clone -b feat/x names a branch that does not exist locally — repo.js:305 already calls that "an entirely ordinary clone" and retries there.
Decision
Mirror that retry in trunkBase, so both age and stacking answer in a single-branch clone instead of degrading to a dash. Covered by a test that builds exactly that clone.
Alternative
Leave it: the spec's error table says a missing merge-base yields null and renders a dash, which is honest. Rejected because it would render a dash for a whole class of perfectly healthy repositories, and Phase 6 runs this against a real projects tree.

stackedOn — two branches at the same commit are unstacked, not a cycle

Context
The spec's rule is "B is stacked on A when merge-base(B, A) is a strict descendant of merge-base(B, trunk)". It is symmetric: a bay cut from A with no commits of its own has the same tip as A, so the rule makes each stacked on the other — a two-docket cycle, from the most ordinary shape there is. The spec's cycle guard would then fire a warning on a healthy fleet.
Decision
Add one condition the spec does not state: a docket is not stacked on a sibling whose merge-base is the docket's own tip. That makes "everything I have is already in you" mean behind-you rather than stacked-on-you, which is also the right answer for a branch that has simply fallen behind its parent. The cost is that a just-cut, still-empty bay reports stackedOn: null — and nothing in git can say which of two identical heads came first, so there is no answer to lose.
Alternative
Let the cycle guard handle it and accept a warning plus an arbitrarily flattened docket on every freshly-cut stacked bay. Rejected: a guard that fires in normal operation stops being read.

Deps tests — experiment (d) split in two, because the stated expectation is wrong

Context
The spec's fourth shape is "B cut from A, then A rebased onto a newer trunk, which must still report B → A because reachability, not dates, decides it". Rebasing A rewrites the commits B was cut from, so after it merge-base(B, A) is the old trunk point — B genuinely shares nothing with A's current history, and reporting B → A would be asserting a false dependency.
Decision
Two tests instead of one. A rebased and B restacked onto it (rebase --onto, the real stacked-branch workflow) must still report B → A, which is the reachability-over-dates claim the spec wanted. A rebased and B left behind must report null, which is what B now is.
Alternative
Track branch identity across a rewrite via the reflog or ORIG_HEAD. Rejected: that is persisted state by another name, and the contract's whole argument for this feature is that it needs none.

Open item — the pair-count cap is 25

Context
The spec leaves the threshold open: "25 dockets in one repository is the working proposal; confirm against what the operator actually sees before hardcoding it."
Decision
Ship 25, as STACK_PAIR_CAP in src/stack.js. The contract's stated working set is 5–10 dockets, so 25 is already well clear of it, and the cap is a guard against pathology rather than a tuning knob — at 25 the pair count is 600 cheap calls, and a fleet that large is unreadable for other reasons first. Phase 6 is the gate that can confirm it against a real tree.
Alternative
Make it configurable via waybill.stackcap. Rejected as a setting invented for a limit no operator has hit yet.

Fixtures — tests/helpers/repo-fixture.js gained two parameters

Context
The spec names the fixture helper as the playground for "committing at controlled dates via GIT_AUTHOR_DATE/GIT_COMMITTER_DATE", but the helper's git environment is a snapshot taken at module import, so setting those on process.env never reaches git. Nothing could build a branch stacked on another branch either: addWorktree always cut from the main checkout's HEAD.
Decision
Two additive, optional parameters — a per-call environment overlay on git, and a start rev on addWorktree. Neither changes behaviour for any existing caller; the whole suite is unchanged and green.
Alternative
A private spawnSync wrapper inside each new test file. Rejected: it would bypass the fixture's GIT_CONFIG_GLOBAL=/dev/null neutralisation, which is the thing that keeps the suite from passing or failing on a developer's machine settings.

Implementation Notes — Phase 4

Decisions taken while de-hardcoding the leg count that the spec did not settle, or settled against a tree that had since moved. Everything not listed here followed the spec as written.

tests/index.js — the new suite had to be registered, and one existing suite was not

Context
The spec's File Changes table does not mention tests/index.js. That file is the entry point node --test tests/ resolves to on Node 26, which treats a directory argument as a path rather than expanding it. A *.test.js not imported there simply never runs under the phase's own acceptance command. Checking it surfaced that tests/doctor.test.js, added by phase 3, was never registered either — node --test tests/ reported 538 passing tests while silently skipping the whole doctor suite.
Decision
Added both imports: ./legs.test.js (this phase's, mandatory) and ./doctor.test.js (a one-line fix to a pre-existing gap that otherwise makes Acceptance check 2 a false green). The full run goes 538 → 576 tests, all passing. Left as a follow-up for a later phase: nothing in the suite asserts that tests/index.js lists every *.test.js on disk, which is why the phase 3 omission went unnoticed.
Alternative
Registering only legs.test.js and reporting the doctor gap without fixing it would have kept the diff strictly inside the phase, but would also have meant signing off a validation command known to be skipping a suite.

tests/waybill.test.js — three fall-off-the-end states, not one

Context
The spec names a single index: 7 site (at :604) as a total wearing an index's clothes. The tree has four: three { leg: null, index: 7, completed: LEGS.map(…) } states at :267, :454 and :601, plus one at :257 that is cleanup's genuine position. The spec's line numbers predate phases 2–3.
Decision
Applied the spec's stated rule rather than its line numbers: all three leg: null states became index: LEGS.length, and :257 kept its literal 7 because it is an index, and moving cleanup from 7 to 8 is phase 5's deliberate edit.
Alternative
Deriving :257 too would have hidden the one line phase 5 most needs to notice when it inserts review before cleanup.

The stamp-only fallthrough test — exit 0/exit 1 over true/false

Context
The spec asks for a booking-owned leg carrying stampCmd and no stampPath, driven at true and at false. Writing the frontmatter value as the bare words true and false invites a reader to wonder whether the parser is coercing them to booleans before they ever reach a shell.
Decision
Used exit 0 and exit 1. They are unambiguously commands, they are shell builtins so no PATH lookup can turn the case into the exit-127 warning path phase 2 added, and the intent — the exit code is the whole stamp — is on the page.
Alternative
/usr/bin/true and /usr/bin/false would also be unambiguous but pin the test to a filesystem layout the rest of the suite does not assume.

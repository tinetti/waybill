Implementation Notes — Phase 2

Portability fixes: exit-127 warnings and tilde expansion. Decisions the spec did not settle.

Fix A — Open Item 1 resolved: status === null is cheap to provoke

Context
The spec's Open Items asked whether a spawn-failure outcome (status === null) could be provoked cheaply, noting that the obvious route — exceeding STAMP_TIMEOUT_MS — costs 10s of suite time, and offering "leave it covered by inspection" as the fallback.
Decision
It can. A stamp of kill -9 $$ is killed by signal, and spawnSync reports status: null, signal: 'SIGKILL' — the same branch a spawn failure and a timeout reach. Verified directly before writing the test; the resulting case runs in ~35ms. tests/bookings.test.js now asserts the could not be executed wording stays distinct from missing binary, so the two failure modes cannot be collapsed by a later edit.
Alternative
A timeout-driven test (correct but 10s), or the spec's fallback of leaving the branch uncovered and saying so in the PR. Both rejected once a 35ms route existed.

Fix B — expandTilde trims before it looks for the ~

Context
The spec specifies expandTilde as a no-op on '', ' ' and undefined, so the existing blank-tier guards keep their meaning. It says nothing about a value that is padded but not blank. Both consuming tiers (src/repo.js configuredBayDir, src/bookings.js configuredBookingsDir) .trim() the selected tier, so a literal-first-character check would leave WAYBILL_BAY_DIR=' ~/bays' unexpanded and then trim it back to a literal ~/bays — reproducing, for one input, the exact bug this phase exists to fix.
Decision
expandTilde tests the trimmed value for a leading ~. Blank and whitespace-only values still trim to '', match no tilde, and are returned untouched, so the spec's stated invariant holds exactly. A regression test covers the padded case in tests/repo.test.js.
Alternative
Check value[0] === '~' literally, as the spec's snippet implies. Simpler by a line, but it makes whitespace meaningful at a tier that has already decided whitespace is not.

Fix B — the src/signals.js precedent cited by the spec does not exist

Context
The spec's expandTilde JSDoc block instructs: "process.env.HOME first, os.homedir() second: the same order src/signals.js:130 uses, and the reason is the same." src/signals.js reads env.HOME and explicitly refuses os.homedir(), returning an empty result when HOME is unset. There is no such precedent. The spec's own Error Handling table, however, does want the fallback ("HOME unset and os.homedir() unusable → returns the value untouched").
Decision
Implement the fallback the Error Handling row specifies, but write the rationale honestly: the JSDoc says HOME is read first, and read at every call rather than cached, because a test handing in a home of its own is the only way to assert this at all. No citation of signals.js. The os.homedir() call is wrapped in a private homeDirectory() that returns null rather than throwing, matching the module's existing "a query never throws, null means it could not answer" convention.
Alternative
Drop the os.homedir() fallback to genuinely match signals.js — rejected because the spec's error table asks for it and an unset HOME under a daemon or a hook is exactly the portability case this phase is about. Or cite signals.js anyway — rejected: a comment that is checkably false is worse than no comment.

Fix A — binaryOf ships without the spec's ?? command fallback

Context
The spec's code sketch is command.trim().split(/\s+/)[0] ?? command. String.prototype.split always returns at least one element, so index 0 is never undefined — for '' it is '', which is falsy but not nullish, so the ?? branch is unreachable on every possible input.
Decision
Dropped the operator. The repo has no typechecker that would want the narrowing, and the house rule is no handling for scenarios that cannot occur.
Alternative
Keep it for literal spec fidelity. Rejected: it reads as a guard against a case a reader would then go looking for.

Fix A — three renderer fixtures in tests/waybill.test.js were re-worded

Context
tests/waybill.test.js:305, :309 and :806 hand the renderer the literal string stampCmd command not found: nope. They are renderer inputs, not assertions about production wording, so they pass unchanged — the suite gives no signal either way. But they would have left the repository holding a spelling of this warning that nothing emits any more.
Decision
Re-worded all three to stampCmd missing binary `nope`: nope. The change is three string literals inside tests whose subject is this exact message, so it traces to the phase rather than being adjacent cleanup.
Alternative
Leave them and note the drift in the PR, per the strict surgical-change reading. Rejected: the next person to grep for the warning text finds two answers and no way to tell which is live.

Scope — Open Item 2: one PR, not two

Context
The spec leaves open whether the two fixes ship together, defaulting to one PR titled for both.
Decision
One commit, one PR. The combined diff is ~150 lines across two source files and three test files, both halves are "portability on a second machine", and both are prerequisites of the same downstream phases (3 and 4). Splitting would double the review and rebase cost for no reviewer benefit.
Alternative
Two PRs, since the fixes share no code. Defensible, and would have been the choice if either half had grown past a screen of diff.

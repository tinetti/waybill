Steps 2 & 4 — link target is the main checkout, not this worktree

Context
Open Item 3 of the spec left this unresolved, and the Failure Modes table warns that npm link run from .claude/worktrees/... yields a dangling wyb. The executing session was itself inside the worktree .claude/worktrees/waybill-feat-work-laptop-readiness, so $PWD would have produced exactly that failure.
Decision
Both npm link and the four /spec:* symlinks were run against the absolute path /Users/jtinetti/Projects/tinetti/waybill (the main checkout, currently 0.8.0 on main). Verified: /opt/homebrew/lib/node_modules/waybill resolves there, and readlink ~/.claude/commands/spec/*.md | grep -c 'plugins/cache' prints 0. This closes Open Item 3 in favour of the spec's own recommendation. Under this repo's worktree-per-branch workflow a worktree-targeted link would die on every branch cleanup.
Alternative
Linking the feature worktree, so wyb would track in-progress branch edits. Rejected: the links would break the moment the branch is retired, and the failure would present as "waybill is broken" rather than "the link target is gone". The consequence accepted instead is that wyb reflects whatever is checked out on main, not the branch under development.

Step 2 — npm's waybill shim was removed so the plugin keeps the name

Context
package.json maps both waybill and wyb to bin/waybill, so npm link created both shims. /opt/homebrew/bin is PATH position 1 and the plugin-cache bin is position 21, so the shadowing described in Failure Modes row 3 was guaranteed here, not merely possible. The spec is contradictory on the remedy: step 2 calls the plugin cache winning "the desired outcome" and npm winning "a Failure Mode … not a success", while the mitigation column says to leave PATH alone and spell out the absolute plugin path.
Decision
Deleted the generated shim /opt/homebrew/bin/waybill (confirmed with the human first). waybill now resolves to ~/.claude/plugins/cache/tinetti/waybill/0.3.1/bin/waybill and wyb to /opt/homebrew/bin/wyb → the main checkout. PATH was not reordered, so the spec's standing constraint holds. Two names, two jobs, as the Technical Approach intends. Caveat for later phases: any re-run of npm link recreates the shim and silently re-shadows the name — re-check command -v waybill after any relink.
Alternative
Leave the shim and use the absolute plugin-cache path wherever the installed build is meant, per the mitigation column. Rejected because it makes the bare name a trap for phase 6's "what does the installed plugin report?" check — the check most likely to be typed from memory, and the one the spec says must get an honest answer.

Step 5 — the work-host credential already existed; only the default host was wrong

Context
The spec describes glab auth status as returning 401 against gitlab.com with the self-hosted work host unconfigured, and marks the whole step HUMAN because of the interactive credential flow. The observed state was different: gitlab.windlogics.com was already logged in as jtinetti, and the only defect was the global default host, still gitlab.com (GITLAB_HOST unset). So the credential half of step 5 was already satisfied and the remaining half writes no secret.
Decision
Confirmed with the human, then ran glab config set -g host gitlab.windlogics.com — a hostname only; no token was read, written, printed or placed on a command line, and no interactive login was attempted. Verified by glab auth status (work host, valid) and by an authenticated read, glab api user, returning jtinetti / active. The pre-existing gitlab.com entry was left untouched per step 5.4. Note that glab auth status now reports only the default host, so the stale gitlab.com 401 no longer appears in the inner-loop probe — the credential still exists in config; it is merely out of frame.
Alternative
Hand the whole step back because the spec marks it HUMAN, or skip the host setting on the grounds that glab resolves the host from the git remote inside a repo and the global default is only a repo-less fallback. Both were offered; the human chose to have it set. Skipping would have left glab repo view <group>/<project> 401ing when run outside a repo.

All three exist: ~/.claude/commands/ contains mar.md, merge-and-reset.md, start-my-day.md and wt.md; ~/.claude/skills/ contains 16 entries including cpr, mr-review and tidy. node is v26.7.0 and the ideation plugin is at 0.15.0, both as the spec states. The spec's inventory is correct as written and step 6 required no action, exactly as specified.

Take the scout at its word and amend the spec's inventory table. Rejected — that would have written a false correction into a gate other phases trust, on the strength of one unverified read.

Step 1 — installed version recorded: 0.8.0, and it is not the eight-leg release

Context
Open Item 2 asks which version the plugin update actually lands on, so phase 6 can assert the eight-leg release specifically rather than "anything newer than 0.3.1". The human ran /plugin marketplace update tinetti and reloaded; ~/.claude/plugins/cache/tinetti/waybill/ now holds both 0.3.1 and 0.8.0, and command -v waybill resolves to 0.8.0/bin/waybill.
Decision
Recorded 0.8.0 as the version phase 6 must distinguish itself from. Critically, waybill help on this build prints a seven-leg route (ideate, bay, refine, contract, specs, execute, cleanup) — so 0.8.0 is not the eight-leg release the contract expects phase 6 to install. Phase 6 must assert the leg count or an explicit version string, never "newer than 0.3.1", which 0.8.0 already satisfies while still being the wrong build.
Alternative
Treat "resolves outside 0.3.1" as sufficient, per the phase-1 checklist wording. Rejected — that is precisely the Failure Modes row "Phase 6 believes it installed the eight-leg route when it did not", and this machine is now in exactly the state that triggers it.

Step 2 addendum — the wyb / waybill experiment no longer differs

Context
The step 2 feedback loop says to run wyb help and waybill help and expect them to differ before phase 6, the working tree being ahead of the installed plugin. Before the update that held sharply: 0.3.1 had three commands and no help verb at all, against the working tree's full route.
Decision
After the update both print the identical seven-leg route, because the installed plugin (0.8.0) and the main checkout (0.8.0) are now the same version. Recording this so the next executor does not read the sameness as a broken link or a shadowed name — the two shims are still distinct and still point at different places, verified by command -v on each. The experiment's premise simply expired when step 1 caught the plugin up.
Alternative
Flag the identical output as a step 2 regression. Rejected — command -v proves the two names resolve to different files; identical output is a fact about the two builds' versions, not about the linking.

Step 1 caveat — 0.8.1 is being cut concurrently, so the recorded version is a snapshot

Context
While phase 1 was closing, another agent was cutting 0.8.1 on chore/release-0.8.1 (a locked worktree under .claude/worktrees/). The version recorded above, 0.8.0, is therefore true as of this run and expected to be superseded the next time /plugin marketplace update tinetti is run.
Decision
Leave 0.8.0 recorded as the observed value, but phase 6 should assert the leg count (eight) rather than a version string — the leg count is the property the contract actually cares about and it does not rot when a patch release lands. Re-run the phase-1 probe at the start of phase 6 rather than trusting this number. Note also that the concurrent release does not disturb this phase's artifacts: wyb and the four /spec:* symlinks target the main checkout, so they follow main forward as 0.8.1 merges — which is the intended behaviour of symlinking rather than copying, not a hazard.
Alternative
Wait for 0.8.1 to land and record that instead. Rejected — the gate is about the machine being in a known-good state, not about pinning a release. Chasing the version would make phase 1 re-run on every patch, and the leg-count assertion makes the number unnecessary.

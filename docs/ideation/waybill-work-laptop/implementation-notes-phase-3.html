Implementation Notes — Phase 3

Decisions taken while building waybill doctor that the spec did not settle, or settled differently. Everything not listed here followed the spec as written.

tests/help.test.js — a forced edit the spec does not name

Context
The spec's Modified Files table lists tests/golden/help.txt but not tests/help.test.js. The --help stays terse case at tests/help.test.js:256-283 pins the banner by count: commands.length === before.length + 1, with the last row asserted to be help. Adding the doctor row makes that six rows, not five, so the suite fails before any doctor test is even reached.
Decision
Widened the pin to before.length + 2 and asserted both trailing rows by position — doctor at -2, help at -1. The literal four-verb before array is left exactly as it was, so the guard's real job (noticing a reworded verb row) is untouched. This is a third pinned list of the same kind as DECLARED and invoking; the spec found two of the three.
Alternative
Appending doctor after help in USAGE would have kept commands.at(-1) pointing at a different row and still broken the count — and the spec explicitly places the row before help.

Check 7 — one plugin-cache row, not a separate skew row

Context
The spec's implementation steps say to "compose the cache row, the skew row, and the PATH row" — three rows. Both worked examples in its own Output Format section show two: a single plugin cache row, and the waybill PATH row.
Decision
Followed the examples. plugin cache is one row with three states: warn carrying cannot locate plugin cache, warn naming both versions on skew, or ok naming the version and its install path. A separate skew row would have had nothing to say in the case that matters most — when the cache cannot be located, there is no version to compare against, so the row would either be blank or repeat the first one's complaint.
Alternative
Three rows, with the skew row suppressed when the cache is unlocatable. That is the same information in more lines, and doctor's whole value is a report that fits on one screen.

The renderer wraps no details

Context
The spec's example output shows one long detail wrapped onto a continuation line indented to the detail column, and its Failure Modes table names "column drift on wide details". But the four numbered implementation steps describe only the row, the fix: continuation and the footer — no wrap — and test 26 asserts alignment and fix placement, not wrapping.
Decision
No wrapping. A long detail runs long. Wrapping needs a terminal width, and there is no honest source for one here: process.stdout.columns is undefined under the ! invocation that is doctor's main surface, so any wrap point would be an invented constant. Alignment is preserved where it is actually load-bearing — the status and label columns — and fix: lines still get their own line.
Alternative
Wrap at a hardcoded 100 columns. Rejected: it would reflow paths and hostnames mid-token in a report whose entire purpose is that a remediation can be copy-pasted intact.

Check 6 counts rebooked legs off resolveBookings, by path

Context
The spec asks for "overlay in force: <path> (<n> legs rebooked), the count from resolveBookings" — but resolveBookings returns the merged map of all seven legs, which is not the count wanted.
Decision
Called resolveBookings exactly as the spec says, then counted the entries whose booking.path lies under the overlay directory. Every Booking already records the file it came from (src/bookings.js:88), so the count falls straight out of the one resolution the rest of the CLI also performs — and the malformed-overlay warn then fires on exactly the errors a real /waybill:* command would hit.
Alternative
Calling loadBookings(dir) directly for the overlay alone. That gives the count with no filtering, but it means re-deriving the anchor and the resolution resolveBookings already owns — the exact drift the spec's "export configuredBookingsDir" instruction exists to prevent.

Two probe functions, so the no-secret rule is structural

Context
The Security Constraint requires that doctor never relay stdout or stderr from gh auth status or glab auth status, and is enforced by one test planting a token. A single general-purpose probe helper returning {status, stdout} would satisfy that test while leaving the output one careless interpolation away from a rendered line.
Decision
Split the helper in two. probeStatus returns an exit code and no streams at all; probeOutput returns stdout and is used only for git --version, openspec --version and glab config get host. The auth probes can only call the former, so a future edit cannot leak a token without first changing which function it calls — which is visible in review.
Alternative
One helper plus a comment. The test would still pass today; the constraint would rest on whoever edits it next having read the comment.

The review cycle ran as a self-review, not the Reviewer agent

Context
execute-spec calls for a Verify-Review-Fix loop driven by the ideation:reviewer subagent. This phase executed inside a subagent, where no Agent/Task tool is available, so no reviewer could be dispatched — the same situation the skill's "reviewer unavailable" fallback describes.
Decision
Fell back to validation-only mode as the skill directs, and added a self-review pass over git diff HEAD against the spec's three load-bearing constraints. That pass produced four fixes: a string concatenation and a pointless template literal in src/doctor.js, a substring assertion in the missing-spec-commands test that would have passed against a check listing nothing, and a new structural case asserting that every fail and warn carries a fix while ok and info carry none.
Alternative
Reporting the phase as failed for want of a reviewer. The skill explicitly prefers the fallback, and all 538 tests pass; a human review of the diff is still worth having.

A manual-test expectation in the spec is wrong, and the code is right

Context
The spec's last manual check reads: CLAUDE_CONFIG_DIR=/tmp/nope node bin/waybill doctor — "says cannot locate, still exits 0". Run against this implementation it says cannot locate and exits 1.
Decision
Left the behaviour as it is and recorded the discrepancy here. Check 4 reads the four /spec:* commands out of the same config directory, so relocating it to an empty path genuinely breaks them — the FAIL row is honest, and the exit code follows the one rule the spec insists on. The expectation overlooked that checks 4 and 7 share an input. Check 7's own rule is upheld: the plugin-cache row is a warn, never a fail.
Alternative
Making check 4 degrade to warn when the config directory looks synthetic. That would need doctor to guess which config directories are "real", and would soften the one check that catches this laptop's actual documented gap.
